# Warmup plan approval and recovery panel

21 October2026. API1ed77a6 and recovery correction6e716b6 precede this owned client checkpoint. Automatic Start stays unavailable.

## Flow

After explicitly saving or recovering a session review, the owned warmup retention panel mounts a separate plan-approval section. Nothing fetches or writes on mount. Users choose a finish window of1,3 or5minutes after the last captured action, see the exact finish date, then explicitly request approval terms. The reader validates the whole original captured manifest, SHA-256, retained identity/creation time, plan and wallet revisions, actions, dependencies, sums, false capability flags and unchanged review lifetime. Server source hashes are opaque content bindings, not browser-verified on-chain proof.

The checkbox starts unchecked and resets with deadline/context changes. Saving replays the current captured view and checks the clock again after asynchronous hashing. It cannot renew a stricter original local deadline. A minimal public recovery ID/hash/deadline reminder must be persisted and read back before the only save POST. No context blob, raw receipt source, key or password is stored there. Saving records plan consent only; it does not unlock a wallet, authorize signing, reserve execution funds or start a session.

Unknown, lost, cancelled or malformed save responses keep the same ID. Recovery uses explicit GET, never repeats the write, and a404 does not clear a potentially pending save. A known unique-review conflict offers explicit recovery of the original saved ID; its GET must match the same plan/review/hash before the local reminder can point to that confirmed record. The saved deadline is not edited or renewed. Reminder-update failure retains the known record for display/copy without granting another save. Clearing a reminder is explicit and requires a new source review before another save; it does not delete or cancel server history.

Preview/read/save work is cancelled on unmount, context change, pagehide, storage invalidation and relevant new receipts. Expiry blocks another approval while keeping historical recovery available. A pending save may already have committed, so its reminder survives cancellation. Bodies are capped at3MiB UTF-8, require JSON and cancel stalled readers with the request signal. Fixed UI errors hide HTML/parser/provider diagnostics. Parent review/retention controls coordinate busy state; no protected shell/token-layout file changes.

## Recovered finished-wallet dead end

The existing historical-review client reader assumed every wallet's further maximum equals buy inputs plus unused reserve. The builder correctly assigns zero further spend to a finished wallet even when some reserve remains. A new regression first reproduced the refusal; the reader now uses actual remaining actions to distinguish active/inactive wallets. Inactive wallets must have zero buy allowance and zero further maximum, while active arithmetic and total sums remain exact. Separate positive/refusal tests cover this shape. Original-context matching still rejects changed manifests; these display checks are not provenance or spending authority.
