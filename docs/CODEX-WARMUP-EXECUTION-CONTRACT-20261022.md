# Versioned warmup execution contract

22 October 2026. Design proposal based on source `6c5099ab5a0f0125dcf487ad905ad9f627caf7e4`. This is an implementation dependency audit, not an executing feature, migration reservation or authority to send. Full Proxima parity remains open.

## Existing boundaries to preserve

- `wallet-warmup-session-v2-consent.ts` admits up to 4,800 captured actions, three qualifications per action, a 30-second minimum gap, one pending action and a 60-second qualification TTL. The approved session has its own expiry. Its authority flags are false.
- `wallet-warmup-session-v2-journal.ts` records begin-review/pause/resume/stop. It selects the first action and reports zero completed actions. Its immutable root, ordered/hash-linked bounded event reads, monotonic timestamps and same-ID recovery must not be weakened to make progress appear complete.
- `wallet-warmup-session-v2-attempts.ts` validates and saves a first-action unsigned packet or refusal. `wallet-warmup-session-v2-runtime-storage.ts` separately binds runtime purpose and observations. They are not executable preparations.
- Committed `0134_wallet_warmup_session_v2_attempts.sql` blocks v2 attempt IDs from legacy preparations, signing intents and receipt tables. Its source context compares the original exact receipt set and amounts, so a newly finalized buy invalidates that baseline. Adding a cursor alone would not make the next action eligible.
- The legacy `wallet-warmup-session-sequence.ts`, replay, action binding and settlement storage are reusable references, not a compatible v2 execution backend. The legacy schemas have different capacity and freshness rules. `wallet-warmup-session-settlement.ts` really re-observes finalized owned signatures/packets/balances; a literal `verified: true` is never enough.

Existing v2 and legacy records keep their format, semantics, isolation triggers and deadlines. Do not upgrade a read request to execution or accept a completed manual trade as a session action retroactively.

## Proposed distinct execution record

Use a new versioned execution root and event stream; exact SQL names/version are to be decided after review. Do not edit committed migrations. Recheck the journal before reserving the next number, currently 0137. Root consent must separately and explicitly authorize an execution-capable session after the required runtime/program/provider qualification exists. Existing v2 consent can identify a proposed plan but cannot become execution consent by reference alone.

An initial internal prototype must remain unmounted, have no signing/API/provider caller and return all authority flags false. Its inputs are evidence supplied by an internal verifier, never arbitrary request-body settlement labels. A test fixture cannot qualify a real provider or execution path.

Root identity: verified owner, execution ID, consent ID and exact consent hash/document, retained plan/revision and wallet revisions, the existing retained review's exact `source_sha256` and source document as initial receipt baseline, immutable full ordered action manifest, per-wallet cumulative buy and fee/rent ceilings, policy version, creation time and original session deadline. No caller-selected mint, wallet, action amount, floor or cursor overrides. New execution consent requires a fresh review and its newly captured/rebased manifest; a v2 consent cannot seed an execution root.

Capture and validate all 4,800 actions and 14,400 qualification capacity without silently truncating to legacy limits. Set explicit per-record and total event/byte limits that leave terminal Stop and unresolved-outcome recovery representable at capacity. No implementation may claim this capacity from manifest parsing alone; the real storage, replay and SQL guards need corresponding tests.

### Per-action lifecycle

1. **Queued:** exact next action from the immutable manifest; never an arbitrary array index from the client. It becomes reviewable only when due, the minimum gap has passed, the session is unpaused/unexpired and dependencies are finalized. A Sell linked to a session Buy remains blocked until that exact Buy's verified acquired amount and receipt are available.
2. **Reviewing:** reserve one pending action atomically against the exact execution head and shared financial wallet reservations. Record qualification attempts independently, with the existing bounded count and pacing. A refused/expired qualification does not complete or skip an action and does not create a broadcast authority.
3. **Prepared:** bind a distinct canonical execution preparation to execution/action/attempt, exact unsigned bytes and hash, runtime evidence hash and expiry, input/minimum, lookup/account/code identities, fee/rent caps and original action/consent. No alternate manual packet. The existing v2 attempt remains read-only; it is not renamed or reused as the execution preparation.
4. **Authorized:** a separately issued short server authorization binds the same packet and source/head, after fresh lifetime/custody/balance/reservation checks. The browser approves and signs the exact reviewed bytes; expiry or a changed context means a fresh review. Qualification expiry and authorization expiry are separate bounds, both enforced.
5. **Submitted or unknown:** record a one-send intent before dispatch. Retain signature/local recovery identity and charge unresolved spend conservatively. Lost responses, unmount, Pause, Stop or expiry never release an unresolved wallet hold, retry a send automatically, advance the action or refund its budget.
6. **Finalized applied or held:** a real owned verifier replays the exact signature, approved packet, network and finalized balances. Bind its immutable source facts and verify them again in the same transaction as event/cursor/budget updates. If evidence is real but cannot safely advance the sequence, retain an explicit held outcome and require recovery; never hide the trade or record a successful action by fiat.

Stop is terminal for new work. Pause/Stop/expiry do not prevent recording an existing in-flight outcome. A failed pre-send review may be retried only through a new explicit bounded qualification; it is not a completed action. Recovery by original ID may read stored state but does not renew any deadline or resend.

### Atomic advancement and baseline

One transaction/guarded statement must check the exact prior execution head, pending action, preparation/intent identity, verified immutable receipt source facts, unique signature/receipt use, wallet/plan revisions and budget before storing the finalized event and advancing the cursor. Concurrent identical requests recover the same event; conflicting action/receipt/head requests fail. A pre-write SELECT alone is insufficient.

Separate the immutable **initial receipt baseline** from **receipts applied by this execution**. New eligibility is derived from that baseline plus exactly these guarded applied settlements. Do not simply replace the baseline with the latest receipt count or omit current receipt-set checks. Unexpected manual/other-session receipts, consumption, plan edits or wallet edits invalidate eligibility for new work and require a newly reviewed source. Historical recovery can still record an in-flight result under its original identity without treating a changed baseline as new authority.

For each applied Buy: input must equal the approved action; record verified acquired raw units/decimals, actual network fee and rent, with one unique receipt/signature. For its linked Sell: use only that Buy's remaining lot, after reconciling every consumption against current receipts; verify mint, wallet/revisions, token program, decimals, source receipt and exact raw amount. No balance-only substitute. Existing saved-buy lots retain their own captured floor and revision constraints.

Budgets use integer raw units, cumulative buys and positive fee/rent debits. Refunds/proceeds must not silently replenish spending authority. Pending/unknown exposures remain charged. An actual finalized outcome over the reviewed ceiling is retained as held/recovery-required, never relabelled failed or automatically granted a larger budget. The next Buy/Sell cannot begin while a hold or unverified consumption is unresolved.

## Required verification before UI integration

- Real disposable SQL with the unchanged committed migration history, not mocks alone: root uniqueness/immutability, action order and source ownership, exact heads, missing guards, atomic races, receipt/preparation/signature uniqueness, source changes during verification and insertion, and direct invalid SQL writes.
- Full Buy then linked Sell then next-cycle replay from the immutable manifest, exact raw budget arithmetic, external consumption/baseline changes, duplicate and wrong-owner receipts, wrong decimals/mint/program/packet and no literal-flag bypass.
- Lost replies before/after commit, cancel during write/recovery, concurrent identical/conflicting writes, Pause/Stop/expiry with an in-flight finalized or unknown result, unresolved holds and no implicit refund/resend/skip.
- Original record IDs and deadlines survive reload/restart. Paging a bounded immutable event prefix must detect gaps, duplicates, truncated batches, altered heads and unsupported versions. Test full capacity and terminal recovery headroom using the actual real storage limits.
- Only after the internal contract passes: authenticated exact-boundary API, unchanged safekeeping/approvals, actionable UI progress with finalized versus held/unknown distinctions, rendered desktop/mobile and interruption checks. Do not expose a cosmetic Start that only records metadata.
- Keep the existing full-runtime 32-slot limit, both code scans, custody/Clock/minimum checks and read pacing. A code-only timing result does not qualify this workflow. Real funded proof and any production deployment remain separately unauthorized here.

The review correctly identified these source constraints; Codex inspected the cited primary source independently:

1. **Receipt baseline and manual visibility.** The initial baseline already exists in retained review `source`/`source_sha256`. Appending to manual receipt tables breaks the committed v2 exact-set checks; hiding receipts in separate tables without a shared lot-consumption projection could allow a later manual Sell to reuse an already consumed lot. A new execution-owned receipt/lot ledger must come with bidirectional exclusion and a shared consumption/progress projection before any send path opens. Merely choosing separate tables is not enough. The exact table/projection design is not implemented or cleared here.
2. **Rent semantics differ.** Initial review nets recorded signed rent; the legacy sequence clamps each new action's rent debit separately. Preserve existing historical accounting. New execution must initially budget gross positive per-action debits without crediting refunds into spending authority. It must check that the newly approved reserve covers applicable outstanding caps and state this conservative treatment before consent. Do not let a session run predictably out of reserve and do not silently change a saved plan's reserve. Matching-account refund credits would require a separately proven lot/account policy, which is not adopted here.
3. **Later-action admission cannot reuse first-action amounts.** Current candidate/runtime checks use the original reserve and zero further buys. A new context must derive remaining capacity atomically from applied debits plus unresolved holds, for the exact next action and lot. It must retain the shared owner `wallet_balance_gates`, three qualifications per action, original deadlines and existing runtime checks; a new per-session pacing gate must not bypass owner pacing.
4. **Held outcomes need precise semantics.** Existing legacy held handling is limited to a known fee/rent overrun. Future held reasons must be closed and enforced from independently verified facts. Unsupported decoding or unverified signature/source data remains unresolved evidence, not a falsely verified held trade. An applied event may advance a cursor; a held event must not. Stop is not reconciliation and cannot delete a financial hold. A guarded reconciliation path is still a required design/verification dependency before execution can open.
5. **Unknown is not proof of non-landing.** The reviewer suggested finalized block height plus missing historical signature status. That shortcut is not accepted as a sufficient proof here: absence can reflect incomplete/lagging provider history. No automatic release is added. A future release protocol needs independently established history/finality/context coverage and exact packet/signature identity, or positive verified landed-failure settlement with actual fees accounted. Until that exists, unknown holds stay conservative and execution remains unavailable. This is a declared liveness gap, not a completed recovery feature.
6. **Mutual exclusion must span all paths.** Execution holds must survive session expiry/Stop and prevent competing manual warmup, imported trading, legacy/v2 and Auto Buy work. Their own admission must also check the existing reservations/intents. All relevant creation/claim paths and their SQL must be traced before selecting final triggers. No new exclusion implementation is certified from this limited review.
7. **A schedule can already be impossible.** The current plan cap is 20 wallets ×20 cycles, at most800 base Buy/Sell actions; extra saved-lot Sells contribute to the 4,800 retained-format bound. Scheduled spacing can be shorter than the owner gate. The session deadline stays bounded by its reviewed schedule plus five minutes; never extend it implicitly. The helper below now detects a necessary lower-bound failure without altering v2 read consent or claiming runtime feasibility.
8. **Large replay and evidence need a different storage design.** Legacy replay has4096 events/4MiB and a60-second source deadline; its15-second gap is incompatible with v2's30-second policy. V2 controls have65536 events/32MiB and reserve Stop bytes, but those bounds do not prove full execution capacity. A trigger-maintained CAS checkpoint and separate bounded immutable proof records must avoid full-prefix replay on every append. Real recovery/audit must still verify the hash-linked prefix, side facts and derived state. Exact capacity and terminal recovery headroom remain unimplemented.

The reviewer proposed a closed preparation gate plus test-only SQL overlays that drop that gate. Such positive tests would not establish a functioning production writer. This proposal is not accepted as a qualification shortcut. A real executable outcome writer must have an actual source-bound verifier/projection; a rejecting stub and a `verified:true` literal cannot prove Buy→Sell progression. Pure reducer tests can establish bookkeeping only and must be labelled as such.

Review limits: it did not read the runtime provider/order/busy implementations, actual Buy/Sell observers, signing, packet validation, legacy journal storage, session-view, finish guards, all reservation migrations, cycle-progress/lot-performance, routes or tests. These remain required before storage/send implementation; reported open Token-2022/minimum-output concerns are dependencies to investigate, not newly confirmed bugs. No authority or migration is enabled by the review.

## Implemented necessary pacing bound

`lib/wallet-warmup-execution-pacing.ts` is an unmounted, provider/storage-free checker for a strictly selected ordered action list and original session deadline. It uses the existing30-second policy, preserves ordering, never backfills earlier than server now, and compares each earliest possible start strictly before the original deadline. It identifies the first unreachable action. IDs must be unique; formats, sizes and timestamps are bounded and canonical. Full4,800 input coverage is tested without truncation.

A fitting result is labelled `qualification-required`, scoped `schedule-lower-bound-only`, with every authority flag false. It omits network, provider wait/retries, user approval, simulation and finalization time, so it cannot prove actual execution can finish. A caller must derive the selection from a newly admitted immutable execution manifest and perform all other checks. No API, consent, UI, scheduler or existing execution path calls it yet. It is not a user-visible fixed workflow.
