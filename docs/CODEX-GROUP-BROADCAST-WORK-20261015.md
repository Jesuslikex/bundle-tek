## Implemented scope

- The immutable launch group is wrapped in a separately reviewed Jito transport manifest with one additional legacy System-transfer tip packet. Every original signed packet stays byte-for-byte identical. Groups above four launch packets are explicitly refused; there is no dropped wallet, split bundle, sequential fallback or instruction appended after signing.
- Tip amount and additional fee cap are explicit new costs. The same original blockhash and last-valid height apply to the tip. The payer must cover its full original launch allowances plus the tip and its complete additional fee cap. This is a point-in-time provider observation, not escrow or guaranteed funds. The original group already reserves the entire payer and active holder wallets within the owning workspace; external movements remain possible.
- Recipient eligibility is pinned to the eight addresses published by [Jito's official documentation](https://docs.jito.wtf/lowlatencytxnsend/#gettipaccounts). Live `getTipAccounts` must match that reviewed profile. No destination refresh occurs during send. A read-only live check at 05:22 BST on 15 October matched all eight accounts: `CODEX-GROUP-JITO-READINESS-20261015.json`. It generated no signatures, used no user wallet and submitted nothing. It does not establish v1 delivery support or inclusion.
- The complete original group and tip are replayed together on the explicitly requested original simulation bank. Original prefix effects must exactly match the fresh independently accounted group replay. The tip must continue the final payer state, preserve plain System custody, debit exactly tip plus observed fee and credit exactly the reviewed tip. Revalidation rechecks owner/project/wallet revisions/folders/metadata, original economics and full deployed code identities. Chunked code collection is not an atomic bank snapshot or semantic audit; upgrades after observation remain possible.
- Original five-second browser group-signing authorization is unchanged. The tip has its own initially unchecked exact-message approval, browser vault access, context guards, original expiry and temporary-key cleanup. Its signed bytes are verified and retained before registration. A failed registration can save the same bytes without signing again. Public signed-tip JSON can be downloaded and restored against the exact saved review. Explicit corrupt-backup discard resets approvals and preserves the unchanged tip message.
- A separate initially unchecked consent authorizes one broadcast attempt of the exact entire group plus tip. A primary-key-protected attempt and its exact consent/evidence are inserted atomically before contacting Jito. A second request returns the retained attempt. Abort, timeout, malformed acknowledgement, lost response or a crash after persistence never produces an automatic resend. A response error leaves the UI uncertain until authoritative reload. A bundle ID is only an acknowledgement.
- Recovery reads exact finalized chain bytes for all launch packets and the tip, and independently checks tip transfer/fee balance deltas. Jito status is supporting evidence only, including when a send response was lost. All successful finalized packets at one common slot with resolved fees can close the pending execution reservation. All-finalized failures with resolved group and tip fees can close as failed. Expired-unobserved closure requires the shared lifetime plus 32 finalized blocks and linked mint absence; unresolved costs stay unresolved, not zero. Partial, pending, missing-tip and unknown outcomes retain reservations, potentially indefinitely pending a separate resolution policy.
- Recovery attestations come from the configured provider and builder. SQL enforces their scope and internal consistency; it cannot independently prove consensus or re-execute RPC reads. Every new terminal receipt retains `economicSettlementVerified:false`, `completeLaunch:false` and `atomicity:'jito-transport-requested-not-proven'`. Finalized pending execution does not claim audited P&L or independently established bundle atomicity. A separately signed tip can land independently if rebroadcast, which the UI discloses.

## Durable guards and ownership

Append-only `0088_pump_group_broadcast.sql` adds immutable transport review, signed-tip, attempt, result, observation and closure records. Guards bind owner, original group, every ordered packet, signed-vector hash, code identity, metadata, raw costs, exact consent, fresh evidence and terminal receipt contents. Expiry checks include the actual height margin and linked mint-absence slot. All 21 required guards must be installed. The old group-only terminal path redirects to tip-aware recovery. Existing reverse reservation checks remain; an additional update guard prevents retargeting an existing reservation into an active group. An event-backed closure preserves the original signatures and atomically changes parent state. A status observation alone never claims reservations have been released.
