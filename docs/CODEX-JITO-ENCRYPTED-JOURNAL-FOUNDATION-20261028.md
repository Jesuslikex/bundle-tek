# Browser Jito recovery journal foundation

The new, currently unconnected browser journal stores a bounded owner-scoped UNKNOWN marker in IndexedDB and can replace it with an AES-GCM-encrypted, cryptographically verified signature. It uses a separate domain-bound PBKDF2 key derived from a normal password, a random salt and IV, immutable context as associated data, a nonextractable key and a cooperative per-owner Web Lock. It stores no wallet seeds or password. The caller must independently validate the existing vault password or explicitly confirm a recovery password before use.

Storage operations wait for transaction completion and use exact nonce-bound compare-and-set. A stale UI context does not prevent an already-returned exact signature from being retained under its original held lock; fresh owner-scoped record checks are required before inspection. UNKNOWN, missing, expired or rejected outcomes never prove that signing did not occur. Retained entries can be removed only after exact cryptographic verification, a fresh authenticated matching server signature and an exact compare-and-delete; UNKNOWN cannot be removed by this API. Bounded discovery returns only non-secret identifiers and status for the current owner, project and session.

Independent Node 24 verification passed 52 tests across journal and recovery files, with TypeScript, scoped typed lint and formatting. Independent source review found no blocker in this standalone scope. A synthetic local Chrome origin exercised actual IndexedDB commits, duplicate insert, nonce mismatch, encryption/decryption, retained-only acknowledgement and competing CAS, plus two-tab Web Lock refusal and acquisition after release. The initial browser fixture used an invalid expiry and was corrected without changing production validation. The final test used generated data only; its test-origin storage was left in place.

**Not integrated:** no signing UI, server attempt reservation or database guard uses this journal yet. It does not protect another device, an older client or a wallet used independently, and it cannot capture a response if the page is destroyed before the wallet returns it. Browser storage can be evicted; password loss or a vault-password change can strand ciphertext. A copied database enables offline password guessing despite the KDF, and an eight-character minimum is not a strength guarantee. Same-origin script/XSS and a compromised device are outside its protection. JavaScript temporaries are not guaranteed to be erased. No real wallet, provider, signing, submission, funded action, hosted SQL or deployment was used.
