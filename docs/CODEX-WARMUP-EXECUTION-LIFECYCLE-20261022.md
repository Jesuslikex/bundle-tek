# Warmup execution lifecycle model

Base source: `4f04ff67243808cca252441f38d60389286cb829`. This implements the new-root bookkeeping step in `CODEX-WARMUP-EXECUTION-CONTRACT-20261022.md` after the shared-ledger audit. It is not mounted, persisted, exposed through an API or connected to a provider/signer. It does not make Generate Activity execute trades. Existing v2 consent and all signing gates are unchanged.

## New manifest and lifecycle

The strict `wallet-warmup-execution-manifest-v1` format has its own root ID, owner/consent IDs, exact versioned policy and source/consent hashes, original timestamps, exact wallet revisions, Buy/fee-rent caps, ordered action IDs and saved lot references. This is a distinct shape, not an upgraded v2 read consent. Parsing a consent digest does not verify that consent exists. Production must derive and verify this entire manifest from new owned consent and original immutable sources before any durable writer uses it.

The model validates unique wallets/lots/action IDs, source order, wallet/mint/program/decimal identity, one full-lot Sell per source, a matching Sell for each Buy, and sufficient wallet caps for all scheduled Buy inputs and gross per-action fee/rent upper bounds. Canonical unsigned integer values use uint64 bounds and BigInt sums. Wallet Buy plus fee/rent caps cannot exceed uint64. Dates are canonical and scheduled action times stay within the original interval. Expiry cannot exceed the last scheduled action plus five minutes; the existing necessary pacing checker must also fit. Source/consent verification must establish that these are the originally approved schedule/deadline, not a fabricated later plan. These are format/economic necessary conditions, not admission of a valid current plan or ownership proof. The 4,800-action format test is synthetic and does not establish that such a source can fit existing review/storage byte limits.

`WarmupExecutionLedger` tracks one pending action, exact ordered cursor, cumulative spent versus pending exposure, per-action qualification counts, per-session qualification spacing, preparation hash/minimum output, authorization identity/deadline, original signed/dispatch identity, and observed outcome references. It has no send callback. A dispatch-intent transition only models the marker a future transaction must retain before an external send; it cannot ensure one network attempt by itself.

- Exact expectedRootSha256, local expectedVersion and monotonic committed clock reject stale/malformed transitions without mutating state. This is not a database CAS, owner-wide pacing gate or shared wallet lock.
- Three qualifications per action and a 30-second gap survive unsigned cancellation. Each qualification has at most the existing 60-second TTL, bounded by original session expiry. Requalification is explicit and cannot follow authorization.
- Authorization is at most five seconds, bounded by the original qualification/session deadline. Exact packet hash and current qualification evidence reference must match. Preparation, authorization and outcome projections retain the qualification binding. Auth and dispatch IDs cannot be reused within their own namespaces. Dispatch binds its exact authorization ID. An unsigned packet hash cannot change its action/minimum semantics; a signed packet hash or signature cannot be reused for a different observation. Settlement must match both the original unsigned and signed hashes. Opaque qualification/recheck/source reference hashes may recur; uniqueness alone would not prove their semantics or freshness.
- Pause/Stop/expiry stop new preparation/authorization/dispatch. Pausing an authorized or dispatched action irreversibly marks that pending state unknown; Resume cannot restore or reuse its pre-pause authorization. Unsigned reviewing/prepared holds show paused, expired or review-expired explicitly, and exhausted qualifications have a separate phase. They do not delete a pending exposure. Late exact signed identity can be recorded only after an explicit unknown transition, without fresh approval or a send. Without a previously retained dispatch marker its later outcome is held as missing-dispatch-intent and cannot advance the cursor. Snapshot phase also derives recovery-required from an expired unused authorization or interrupted authorized/dispatch state, without erasing the original record or renewing a deadline. A normally dispatched action awaiting finality shows awaiting-outcome even after the signing window expires, with its lot still unavailable; once stopped/paused/session-expired it requires recovery. Snapshot and lot use the same recovery predicate. Late outcomes remain recordable after Stop/expiry.
- Explicit unsigned cancellation is limited to reviewing/prepared states, before authorization or signed identity. It is bookkeeping only; production must independently establish that no signing authority or packet exposure already exists before releasing its durable hold.
- Applied Buy adds an exact receipt-linked lot and gross actual fee/rent cost. The linked Sell consumes that lot's entire captured remaining units once. A lot projection explicitly separates booked remaining units, held units, zero available units while pending, and observed but unreconciled consumption. It cannot advertise a held partial Sell as spendable inventory. Held Buy acquisition is separately visible with zero available units. Applied/held outcome references remain detached in a bounded model map; these references are not the actual retained source proofs required by production. Sale proceeds and rent refunds never replenish Buy/fee authority. External consumption is not reconstructed; shared atomic lot admission remains mandatory.
- A missing dispatch marker, input mismatch, minimum-output violation, gross fee/rent overrun or a positive landed-failure observation is held without advancing. Observed values/source reference remain on the held action. Exposure is at least the original cap or larger observed debit; an overrun can show negative remaining capacity. No success-looking verified flag or absent-history release is manufactured. Held reconciliation is intentionally not implemented; it remains a dependency, not an available recovery operation. Likewise, an expired authorization that never produces a recoverable signature stays blocked: this model has no independently proven unsigned/non-landing release path. It is a known liveness gap that prevents production enablement, not a completed recovery workflow.
- Snapshot, lot and outcome projections are detached. They are not trusted serialized checkpoints or proof of historical replay. Canonical manifest hashing binds content only. Event hashes, signatures and outcome fields require real packet/runtime/finalized-balance verification and same-transaction source guards before production use.

## Capacity and remaining storage design

The model policy bounds accepted transitions at 76,100 and stops ordinary work four transitions early. This is 4,800 x15 nominal worst retry/unknown-observation steps, plus4,096 extra model control steps and four terminal observations. Earlier65,536 was insufficient for every nominal cancelled-attempt path and is not the final new-root policy; no existing v2 or runtime limit was changed. The reserved tail permits Stop -> unknown -> late signed identity -> outcome without reopening ordinary work. The tests exercise that exact tail from an authorized action with Stop first/last, and separate dispatched, held and unsigned tails. The authorization is issued only after consuming ordinary control headroom; pausing after it must revoke reuse. The full synthetic path includes20wallets,400Buys,4,800actions,14,400qualifications, two prepared unsigned cancellations per action, then successful dispatch/unknown/outcome, exactly72,000 transitions. Unbounded repeated controls or unqualified reserve/cancel loops can still exhaust finite capacity; the projection says model-capacity-exhausted and never promises all arbitrary paths can finish. This is an in-memory event-count contract, not proof of SQL byte limits, append capacity, persisted audit recovery, or every durable-state race.

The model does not prove consent age or the actual source plan's maximum total duration. New owned root admission must bind its original fresh consent and plan schedule; this parser cannot make an old or fabricated source valid.

Next work must define and test actual compact checkpoint/proof storage, durable manifest/consent lineage, the precise all-family bidirectional reservation guards and shared receipt/lot admission. No migration number is reserved here. Reusing ordinary receipt tables still needs preparation/finalized intent/event lineage and must exclude manual signing paths for execution-bound records. Only after those production guards and real outcome writer are proven can provider qualification, browser approvals, one-send recovery and honest running/progress UI be connected. Existing 32-slot/both-scan/custody/Clock/minimum checks remain unchanged.
