# Exchange funding review UI

Ownership notice before UI edits: Codex will add `components/launch/exchange-funding-review.tsx`, its CSS module/test, and a small conditional slot in `components/launch/funding-planner.tsx`. The slot is only for a selected saved CEX draft. It will replace the inappropriate direct-wallet preparation panel for that draft; Wallet funding retains its existing path. The other Bundle chat owns the Volume work and its REA/browser session. No shell, token, wallet/vault/warmup or other Claude-owned file is part of this change.

The review will show the receiving funder, exact provider deposit cost, expected SOL payout, exchange cost, distribution total and remaining unallocated payout. Provider setup and unsaved/archived/missing-funder states will explain why quoting is unavailable. Quote retrieval is explicit. Mounting the panel may read authenticated configuration, saved wallet revisions and previously saved quote history; it must not contact an exchange provider or create an order automatically.

Saved evidence is historical and may be stale or expired. A changed draft, receiving funder, amount or component lifetime cancels pending work and clears a current review. Parsing must refuse inconsistent amounts or unexpected authority flags. API rate references stay on the server. The later deposit, payout verification and distribution steps will be described honestly as unavailable until implemented. This checkpoint must not offer a deposit address or any action that unlocks a wallet, creates a provider order, signs or funds.

The user approved using Smoke's exchange-funding approach. This is still only one part of Proxima-style funding and Front/Back launch execution; the complete goal remains open. No provider settings, credentials, hosted SQL, push or deployment are included.

## Implemented result

Valid CEX drafts now show the exchange review panel. Unsaved/archived/dirty drafts explain why a quote cannot be requested; unsupported assets and proxy routes explain the native SOL boundary. A receiving funder is labelled as the payout destination and must match an active saved wallet revision. The user enters the expected net payout in SOL, at least the distribution total. Quote requests happen only on a button click. Configuration, wallet membership and latest owned history are read independently of a provider quote; missing history storage does not hide the clearer server-setup state when the provider is disabled.

The response parser is shared between the service, historical reads and the browser. It validates public fields, authority flags, timestamps, exact u64 atomic amounts and both accounting identities. Opaque provider references and unexpected fields are rejected. The API now supports authenticated setup status without disclosing credentials and latest owned history by draft; these reads never request a provider quote. The server still revalidates the actual owned document and wallet; browser validation is not authority.

The panel shows deposit cost, expected payout, included exchange cost, saved distribution and unallocated payout, plus expiry and historical/stale labels. Its four-step list makes the remaining Deposit / Verify payout / Distribute steps visible while explicitly stating they are unavailable. No approval checkbox, provider order creation, payment address, wallet operation or new execution permission was added.

A serialized context key remounts the review when the draft, saved revision, enabled state or reload changes. Cleanup aborts its own reads and quote requests; editing the payout also aborts an in-flight quote. Late results cannot become the current review. Expiry uses a bounded timer; no polling or automatic provider retry is introduced. Recoverable rate-limit, HTML/service and sign-in errors use known UI messages rather than parser/provider payload text.

Manual drafts previously offered preparation that the backend only accepts for Wallet sources. They now explain how to choose Wallet and save the funder; only Wallet drafts expose direct transfer review. The existing Wallet path retains its consent, simulation and signing checks. Distinct review keys also remove an existing sibling-key collision between Solana review and devnet execution panels.
