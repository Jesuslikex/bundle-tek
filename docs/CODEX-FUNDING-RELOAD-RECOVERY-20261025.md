# Funding draft save recovery across reloads

25 October 2026, source base `5b4464f`. This fixes a verified funding-draft interruption gap: the original save request existed only in React memory, while remounting generated a new draft ID. A lost acknowledgement followed by reload therefore lost the original recovery coordinates. The existing funding CRUD and saved-history APIs are reused; no transfer, provider, signing or execution path is added.

## Behavior

- Before a POST, the hook admits and detaches the exact mutation, computes a purpose-separated canonical document digest, and retains a versioned recovery reference. Only owner namespace, draft ID, action, expected revision and document hash are stored. Allocations, addresses, document text, packets, approvals and signing data are not stored with that reference.
- An exclusive Web Lock serializes claim/readback/dispatch and exact-record removal across tabs in the same browser origin. A pending reference blocks a different save. Missing or corrupt storage, missing browser lock support, or an unverified account scope disables new writes with a readable explanation; saved reads remain available. These are device-local controls, not a cross-device or financial reservation.
- Stopping the wait or leaving the screen aborts local waiting and releases the browser lock even if a transport ignores abort. A dispatched save can still finish on the server, so its reference remains. No timeout, reload or history read automatically POSTs again.
- After reload, Check original save makes an owner-bound exact-ID GET. Only the original next revision, archive state and canonical document hash confirm the save. A later or different winning revision fences the original CAS revision and is reported as conflict. Missing/equal revisions remain unknown. Restored history does not select or overwrite the new editor automatically; Open saved plan is an explicit action.
- The original full request remains only in the originating page's memory. The existing manual exact-request retry is available only while that payload and verified account/storage are still present. Reload never reconstructs or resends a funding payload from a hash.
- The API exposes a stable opaque owner namespace in a no-store response header. New recovery/write requests echo their captured namespace; a mismatch is refused before SQL. Ordinary owner-filtered SQL remains the real authorization boundary. The namespace is not a credential or signing grant, and older clients without the optional header retain their existing owner-authenticated API behavior.
- Account discovery uses an unscoped authenticated list GET. Switching to a different verified account clears old editor/selection state while leaving that account's retained reference intact under its own namespace. Transient sign-in failure or an unreadable acknowledgement does not erase an unknown attempt. Returning to the original account rediscovers its reference.
- A structured, exactly bound first-request account-mismatch rejection proves that particular POST was refused before writing. It may clear only that new attempt, under its lock. A later rejection of a retry cannot clear an earlier unknown save. HTTP202 is not treated as a committed acknowledgement; an exact saved read is still required.
- Recovery controls distinguish stopping a save wait from stopping a read. Phone controls wrap and have44px targets without hiding content.

## Remaining limits and release boundary

A missing row or unchanged revision after the original payload is lost cannot establish terminal failure. It stays held. A terminal cancel/revision-fence API is not implemented; a reload is not proof that a delayed request cannot finish. Another tab can also retain an older in-memory reference after the originating tab conclusively clears its own persisted record; full page reload rereads current storage, while same-scope list refresh deliberately does not erase known unknown outcomes. There is no automatic abandon, refund, lease release or new transaction authority.

Hashes are identifiers, not encryption. Someone with access to this browser's local storage could test guesses of a document or link a known user ID to its namespace. References survive sign-out to permit recovery; they can reveal that draft saving was used. No claim of hidden wallet ownership or private transaction routing follows.

No schema migration, application/hosted SQL, deployment, provider/credential/cron change, real wallet unlock/sign/send, funded test or strategy run occurred.
