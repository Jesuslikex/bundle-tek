# Exchange order consent and recovery ledger

This checkpoint continues the user-approved reuse of Smoke's exchange-funding approach. It adds an internal owner-scoped service, strict order/consent/provider-response models, and additive migration 0104. No API, UI or live provider adapter calls the new service. Existing quote and order-creation authority flags remain false. Provider creation and lookup in tests are injected synthetic callbacks; this is not evidence of a working ChangeNOW account or a live exchange order.

## Implemented boundaries

- A review captures the exact immutable saved quote, refund wallet/revision, creation and expiry, and an owner-bound SHA256 content fingerprint. The fingerprint is not a signature or authentication token. The future route must authenticate the caller and supply the trusted owner; request bodies cannot select another owner.
- The saved draft/document/timestamp and active funder/refund wallet revisions must still match. Both addresses require existing owned wallet-control proofs. The initial private-transfer contract uses a separate proven refund address. This is a conservative integration boundary, not a claim that every provider requires distinct refund/payout wallets. Those response fields and supported combinations still require live qualification.
- Consent records four acknowledgement facts: exact amounts/network, provider custody, possible verification and the reviewed refund destination. A future UI must collect a separate, initially unchecked order-creation approval covering those facts; no checkbox or approval UI is delivered by this checkpoint. It must remain separate from any deposit signing approval. Consent is bound to the exact review fingerprint and cannot be renewed by replay.
- Authorization lasts strictly less than five seconds from the saved approval. Code and the database independently enforce the boundary; the service rechecks time immediately before transport entry, including clock reversal and expiry during the database claim. Capturing an expired review is also refused.
- An immutable attempt is claimed before transport entry. Duplicated calls, pending calls, cancellation and uncertain outcomes cannot invoke creation a second time. A new quote cannot bypass the retained attempt for the same funding draft.
- A syntactically valid provider reference is persisted before decoding the rest of the creation response. Changed amounts, native asset/network, payout/refund destinations, deposit address reuse or unsupported payment tags keep the attempt unresolved. The raw provider response/error is not stored or returned. If storage itself fails after an external provider accepts a request, the attempt remains unresolved and the reference may be unavailable; this is not an exactly-once guarantee for the remote provider.
- Reconciliation uses only that retained owned provider reference. It never calls creation. It checks complete source/destination SOL network fields, both exact amounts, refund/payout targets and stable deposit address. A validated recovery observation can resolve the creation identity even after archive/expiry, while keeping all payment permissions false.
- Provider reports are separate from on-chain receipts. Finished is `payout-unverified`; refunded is `refund-unverified`; failed, verification-required and processing are distinct states. A stale concurrent status response cannot replace a retained terminal report or change the known deposit address. Code and database guards enforce this.
- Public state never exposes the rate reference, provider order ID or deposit address. It exposes no transaction packet, signer, execution authorization or deposit instruction. All order creation, deposit instructions, funding, signing and execution flags are literal false in both the model and stored evidence.

## Storage and remaining work

The six new tables retain immutable reviews, approvals, attempts, provider references, initial results and status observations. A current-context view and insertion guards check ownership, exact consent, proofs, revisions, expiry and five-second claim freshness. Updates/deletes of financial history and deletion of its source quote are refused.

The current one-attempt-per-draft latch is deliberately retained. There is no closure/release path yet, including for a claim that never entered transport. The initial result records whether transport entry occurred so that future recovery can distinguish it from an uncertain external call. Independently verified payout/refund receipts and an append-only closure/release protocol are required before repeat funding can be enabled. Do not remove the latch or retry creation to work around an unresolved attempt.

Still required: authenticated same-origin/size-limited/rate-limited API integration, shared provider request budgets for creation and status, the concrete fixed-origin adapter and current provider-contract qualification, public response decoding and review UI, approved configuration, deposit instruction validity, separately approved deposit signing, independently finalized deposit/payout/refund receipts, active-wallet reservations where spending occurs, release of completed holds and the approved distribution handoff. The guarded local HTTPS origin also currently refuses exchange quote POSTs and funding saves; its owner must review a narrow allowlist patch before real local quote QA. No guard was changed here.

No provider credential was read/copied/configured. No browser or live provider call, order, wallet unlock, signature, payment, push, hosted SQL or deployment occurred. Broad Proxima and Front/Back funding parity remains incomplete.
