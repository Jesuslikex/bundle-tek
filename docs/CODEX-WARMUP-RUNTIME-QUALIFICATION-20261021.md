## Current source map

- `lib/wallet-warmup-session-provider-core.ts` captures the exact action/plan/budget, validates current source around quote/simulation, and applies token/native/provisional fee bounds. Its default simulation does not request full settlement evidence. Legacy behavior must remain identical.
- `lib/imported-swap-simulation.ts` can independently bind selected token accounts, mints, wrapping/rent and lookup observations. The richer mode still relies on provider pre/post balance metadata, and does not gather Clock, complete executable identities or the stock collector's full final custody/lifetime proof.
- `lib/warmup-signing.ts` plus `warmup-native-settlement.ts` contain the existing setup/wrapping/cleanup and settlement checks. Their successful return is narrower than complete runtime qualification. Do not use the function name or a successful simulation as permission to sign.
- `lib/pair-order-review.ts`, `pair-order-simulation.ts` and `pair-order-collector.ts` establish decoded top-level instructions, genuine protected account/mint/Clock/Rent state, raw simulated writable post-state and final custody/mint/lookup/lifetime checks. The collector still imports the complete ImportedPairWalletPreflight type.
- `lib/pair-runtime-preview.ts` brackets that simulation with both complete executable scans, detects executable/writable scope changes and performs final protected-state/Rent/lookup/lifetime/network reads after the second scan. Its result deliberately leaves semantic audit, trusted policy, inner-instruction policy and all signing/execution flags false.
- `lib/pump-group-code-identity.ts` is the common bounded full-byte reader. Its default is one read at a time. The pair collector explicitly chooses four; no extraction may silently move group or warmup onto that stock-only profile.
- `lib/pair-stock-clock.ts` admits +1 only on server-recorded stock responses and propagates the later floor. Ordinary unscoped Clock readers require exact equality. Warmup must retain exact equality; no new implicit stock wrapper or environment profile is allowed.
- `lib/pair-trusted-programs.ts` is a separately pinned stock policy. Complete code identity is not a semantic audit or proof of a warmup policy. `pair-order-first-service.ts` explicitly evaluates that policy against both scans; its flags must not be inherited by a warmup adapter.

First extract a genuinely generic internal runtime input boundary from the economic instruction/simulation collector and runtime bracket. It must carry real asset/mint policy, wallet/custody/funding evidence, exact unsigned order/reference bounds, context digests and finite expiry. It must not require a made-up imported project ID, catalogue claim, pair DTO or wallet preflight to make warmup compile. Existing imported-pair wrappers continue supplying their original genuine evidence and keep their result formats/hash inputs, source checks, stock options and all runtime conditions unchanged.

For a type-only prerequisite, compare emitted JavaScript for every changed existing module with14687e7, and run the relevant actual callers before any commit. A looser TypeScript input is not a new authorization boundary: HTTP ownership/source admission, runtime data checks and false authority literals remain mandatory. Do not add an uncalled substitute validator and label it integration.

Then connect an explicitly requested runtime mode to the actual owned v2 attempt workflow. It must count the same approved attempt and cooldown, run one simulation, and persist/recover the exact packet and bounded runtime evidence atomically. It must not perform a second hidden provider run from GET or an already retained preview. Missing/unknown/cancelled outcomes preserve the original ID. Maintain the25scooperative provider budget,60s/original-finish lease,30sgap,3/action and32-slot bounds; expiry is a refusal, not permission to widen them. Older initial terms or preview-only consent must not be silently relabelled as an execution grant.

0134 is committed and immutable. If the selected protocol needs runtime-request binding or supplemental outcome storage, claim0135before writing a new additive migration, with exact source/lease/purpose/packet/head guards and an atomic write protocol. Do not bridge these IDs into ordinary preparations, signing intents or existing receipt tables. Do not attach provider outcomes to the control head or race away Stop. UI must distinguish a preview, observed runtime evidence, trusted policy and signability.

Full financial holds, a fresh short exact-packet browser authorization, one send attempt, finalized/unknown recovery, action/budget advancement and long-session orchestration remain required. These are not replaced by the extraction or runtime observation. Alternative routing requires real decoded instructions; no platform-usage spoofing or program-ID-only allowlisting.
