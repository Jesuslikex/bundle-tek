18 October 2026. Continues `7b15285` native Pump route/unsigned simulation checkpoint. User scope: program validation and durable reservations, execution disabled; no funding, transactions or deployment.

## Program validation

New `volume-bundle-programs.ts` reconstructs the exact construction and route, then brackets the real unsigned simulation with **two complete full-byte code collections**, using the existing bounded `collectPumpProgramIdentities` implementation without changing it. The required vector is exactly Pump, Pump Fee, SPL Token and native System. Both scans must match a separately supplied server policy byte-for-byte, including address, loader, ProgramData link, deployment slot, upgrade authority, code SHA256, code length and identity kind. Missing, extra or reordered identities, unknown loaders, changed headers/authorities/code and a total span above 32 slots refuse.

The simulation's actual pre/final program account reads are also bound to the first code scan: loader and ProgramData links must match; complete native/legacy bytes must match the pinned hash and size. The scope is cancellable, bounded to 30 seconds / 160 allowed read/simulate calls, and cancels its own pending work on exit. No sign/send method is accepted, no default configured transport exists, and captures cannot enroll themselves into policy.

**Production policy deliberately remains `null`.** No Volume-specific Pump/Fee binary hashes have been separately reviewed here. The default path rejects before any RPC. Tests inject a clearly labelled synthetic server policy and synthetic transport; this is not a production pin set. Results retain semantic-audit and transport-qualification limitations, with signing/execution false.

The final unsigned-simulation live snapshot now also compares Rent alongside all compiled accounts (Clock remains independently validated). This closes an omission where the simulated Rent was checked but the final live Rent was outside the equality slice.

## Durable storage and concurrency

- New isolated-generated schema `db/volume-bundle-schema.ts`, its export and append-only migration **0105** add immutable session plans, round reservations and retained state events. Sessions bind owner/project/revision/mint, exact reconstructed plan/hash, wallet/proof revisions and total session tip cap. Saving a session alone does not hold wallets or funds.
- `volume-bundle-reservations.ts` is server-internal with no API/UI consumers. To reserve, it reads the owned saved context, collects fresh program-validated runtime internally and inserts the exact proof. It never accepts a client-supplied runtime/simulation. Production policy remains unset, so only the synthetic test dependency can reach a successful new reservation in this checkpoint.
- At the exact SQL insert, triggers recheck current project revision/archive/mint and wallet revision/archive/ownership proof, session/round/wallet identity, full plan, fresh disabled runtime and expiry. Exact per-round tip caps and the total cap are enforced atomically. Partial unique indexes permit only one active reservation per round and one per owner/wallet. Identical retries return the existing durable identity; concurrent different requests cannot double-reserve.
- Holds reserve the entire round tip cap, not just the candidate's chosen tip. Explicit cancellation releases only an unsigned `held` reservation. Expiry alone never releases a hold. A conservative `attempted` metadata marker retains the cap and wallet indefinitely; it is not an actual submission or approval. There is no attempted-to-cancelled, automatic timeout recovery, settlement release or retry/reset path. Marking an attempt requires a fresh hold and current parent context.
- Append-only events, immutable identities/proofs and retained sessions/reservations prevent erasing history or reactivating cancelled attempts. Cancel versus attempt uses SQL state predicates, so only one transition wins. Unsigned cancellation stays available after parent archival/revision changes for safe cleanup.
- Additive reciprocal SQL guards block inserts and updates across existing shared Solana locks, scheduled Volume, organic holder sequences, Pump launch/group reviews, stock pair executions, token supply actions (including `signing`) and active Counter proposals. Existing schemas, enum scopes, triggers and historical migrations are not rewritten. Different owners retain the existing owner-scoped locking model.

## Limits and next work

No live RPC, live unsigned simulation, user wallet/vault access, signature, funding, transaction submission, provider/credential/cron change, remote SQL, push or deploy. Synthetic binaries are fixtures, not executable Pump acceptance or a semantic audit. Full-byte collections have the existing documented multi-read/same-slot rewrite limitation and do not establish an atomic bank proof. Transport/source/Clock/resource qualification, separately reviewed production code pins and fresh complete account/fee policy remain necessary before real acceptance. Execution and signing remain hard-disabled independently of policy matches and reservation success.

There is no authenticated UI/API integration, browser approval, signing, broadcast, Pump-aware finalized recovery or durable settlement accounting/release yet. The generic finalized receipt verifier still does not acquire direct-lamport Pump sell parity from this work. Any later execution/recovery must revalidate the exact owner/session/revision/proof/reservation/attempt, preserve uncertain holds and verify actual finalized costs before an atomic terminal transition.
