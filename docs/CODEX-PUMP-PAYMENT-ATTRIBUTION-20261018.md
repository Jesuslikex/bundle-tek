## Computation and scope

The owner service first performs the unchanged full `parsePumpGroupReceiptEvidence` admission and replay. The new projection rebuilds the exact owned group and reads the installed v1 transaction-message SDK's instruction headers/payloads. It compares program, account order and data bytes with the rebuilt packet, then checks CPI account indices, increasing outer indices, bounded call depth and caller-available account scope. It does not treat v1 messages as legacy `instructions` arrays.

Only the supported System instruction codecs are interpreted: transfer, create, prefunded create, allocate and assign. Fixed instruction data must be consumed exactly. Setup payments require the expected target/payer/program owner and a matching positive-space allocation/assignment in that outer scope. Known creation accounts, buyer token accounts, buyer volume accounts and token-quote buyback accounts have separate role bindings. Other System operations, unsupported setup paths, missing metadata or unexplained wallet changes make the affected packet unavailable. No reviewed ceiling or simulation amount fills that gap.

For SOL quotes, purchase payments must originate from the exact buyer under its reviewed Pump buy instruction and go to the expected curve or buyback address. Each tracked wallet's SOL change must reconcile with the decoded outgoing payments and its actual packet fee. Incoming native credits/refunds remain unqualified: the code does not mistake gross outgoing transfers for net purchase spending. Failure receipts count only the observed network fee after the existing failed-effect checks; attempted CPI transfers and token changes are rolled back and do not become purchases or setup costs.

For token quotes, buy spending is the observed net debit of that buyer's exact quote account in its reviewed buy packet, retaining the existing owner/program/mint/precision checks. Native movements still need the setup/fee reconciliation. This does not independently decompose SPL transfers into venue/principal/transfer-fee components or prove venue economic settlement. A positive recorded token acquisition and positive quote debit are required for a classified buy. Non-buy participants cannot silently receive a purchase attribution.

The actual fee payer bears each packet fee in this report. Shared fee/tip allocation is deliberately absent, not implicitly equal or proportional. All arithmetic uses canonical integer strings and BigInt. The public summary accepts the existing builder's bounded maximum of201 packets instead of the earlier arbitrary64 display limit; this does not expand packet construction or signing limits.

### Prefunded token accounts

A funded but uninitialized account may have no pre-token metadata. It is not generally safe to replace missing metadata with zero. The projection can establish a zero starting token amount only for an expected associated token account with a supported successful allocation/assignment to Token-2022, sufficient allocated space, no earlier outer access to that account, no contradictory pre-token entry, and exact post-token owner/mint/program/precision/amount metadata. CPI accounts must remain within their outer scope. Missing custody fields or contradictory starting metadata refuse the inference. The wallet row explicitly records when this creation evidence supplied the starting amount.

Prefunded creation's declared lamports are an additional transfer, not the destination's total balance. A fully prefunded creation with no payer therefore does not charge that old funding again. Separate transfer/allocate/assign setup is also supported. No historical rent minimum or refund right is inferred from a present-day RPC call.

Primary references checked18October2026: [RPC inner-instruction structures](https://solana.com/docs/rpc/json-structures), [SIMD0312 prefunded creation design](https://raw.githubusercontent.com/solana-foundation/solana-improvement-documents/main/proposals/0312-create-account-allow-prefund.md), and [Agave System allocation/assignment implementation](https://raw.githubusercontent.com/anza-xyz/agave/master/programs/system/src/system_processor.rs). The installed System0.13.0 codecs and v1 SDK definitions were inspected directly. The proposal's status and generic runtime sources are not evidence of current mainnet activation, Pump execution behavior or v1 transaction availability. These rules are used conditionally for supplied retained metadata, without enabling a transaction path.

## Authority and retention

The raw version-one receipt document, its hash and all existing storage/migration guards remain unchanged. The breakdown is computed from that immutable source on read. Actual HTTP-to-SQL tests confirm that reloading makes no provider/configuration call and changes neither source bytes nor hash. The public response includes a display-only projection bound to its original evidence hash. Legacy summaries without that optional projection remain readable.

The model withholds acquisition-basis verification, rent-recovery verification, venue-fee split verification, tip coverage and execution authority. A complete wallet-debit report is not economic settlement, code-identity qualification, current holdings, P&L, lot admission, tax basis or signing permission. Signature verification authenticates transaction bytes; provider-reported execution metadata is not itself cryptographically authenticated consensus/bank evidence. All existing signing, execution, reservation and settlement paths remain unchanged.

No schema or migration was added in this checkpoint. Receipt history still depends on installed migration0113 from `dd63e24`; it was not applied to the user's application database here. Only disposable test databases were written.
