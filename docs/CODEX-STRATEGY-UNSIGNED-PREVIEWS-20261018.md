## Behavior and boundaries

`StrategyCandidateCheckPanel` now offers an explicit unsigned preview for a due DCA candidate or a deliberately selected Limit pool whose current condition is met. The dedicated `strategy-previews` POST route authenticates the user before parsing a bounded exact-key request: project/draft IDs, held-capacity revision, hold ID and condition pool (null for DCA). Wallet, mint, amounts, decimal precision and strategy terms come from owned saved context, not client authority fields.

The service checks the active draft/project/wallet roster and held slot, reads current input balance, obtains an exact wallet-bound Metis unsigned order, inspects the actual canonical packet, runs the existing unsigned simulation and native settlement verifier, and checks observed SOL against the maximum setup/fee/rent debit. Context fingerprints and timing are checked around asynchronous stages. Limit uses the selected pool's fresh exact market cap before balance/order work and again after simulation; an unmet/missing cap or changed context withholds the preview. The condition pool is explicitly a market-condition source; Jupiter may route through other pools. This does not claim that the selected pool is the execution venue.

One preview acquires the existing owner wallet-read gate for 15 seconds. A successful Limit preview makes exactly two market observations and does not reuse or bypass the lightweight condition endpoint's separate gate. This prevents an immediate preview from being blocked solely because the user just checked conditions. It does not claim one shared global market-read budget across the two endpoints. A 25-second server deadline rejects cancelled/non-cooperative work and prevents late publication or follow-on simulation. No automatic retries or refresh are introduced.

The response contains a separately named, strictly rebuilt DTO: exact quote input/minimum, packet fingerprint, balance observation, simulated fee/rent/debit, condition snapshot, bounded expiry and preview fingerprint. It contains no packet bytes, signer, approval/preparation ID or financial history write. Only the existing read-rate gate is mutated; the held planning-capacity ledger stays unchanged. All funding/signing/execution flags remain false. This transient checksum is not a server approval token and has no signing consumer. No migration was added.

The child UI makes requests only on explicit clicks, keeps technical details collapsed, and removes expired amounts. It uses the server request-start time plus client monotonic elapsed time to bound the usable preview window without double-counting server work. Parent check/pool/context changes, hidden/offline state and cancellation abort/discard stale results. Unfunded input and insufficient fee/rent SOL return actionable refusals without requesting funding or approving a transaction.

## Local verification guard

The guard now permits bounded exact-key strategy checks/previews and manual market, candle and trade observations needed for the peer's real-app chart check. Existing authentication, origin, current-context and provider gates remain in those APIs. Candle mode is limited to latest/older and rejects follow; unknown action/packet fields, malformed selectors and all financial routes remain blocked. A market request has the same body whether initiated manually or by a scheduler: this filter does not prove user intent or detect scheduled market refreshes. No market/candle feed is started by this work.
