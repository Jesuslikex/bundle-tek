# Mixed-loader code packing for stock evidence

The explicit stock four-read path previously collected legacy-loader code from offset0, then upgradeable program data from offset45. Each loader class started its own sequence, leaving short legacy code in a separate request even when it could share the first bounded account read with upgradeable data.

When the explicit four-read profile contains both loader classes and every declared account size is known and validated, the collector now reads both at common absolute offsets starting at0. Upgradeable data's initial45 bytes must exactly match the already validated deployment header before being removed from the code stream. Every ELF byte after that header is hashed in original order, with exact declared-length checks. Legacy code is hashed from its original first byte. The final executable/header/network rereads and the separately repeated full post-simulation code scan remain present; no cached or prior code bytes are reused.

Only that mixed, declared-size stock branch changes. Default one-read group signing, single-loader profiles and unknown-size fallback retain their existing offset schedule. The same four-read concurrency ceiling, 720KiB maximum slice, 1MiB aggregate raw bytes per request, 10MiB per-program code bound, 32MiB total code bound, 300-read deadline/budget, requested-floor checks, 32-slot rule and provider pacing apply. The extra45 header bytes count toward the raw response/packing bound but are excluded from codeBytes and the ELF digest, as required by the original identity format.
