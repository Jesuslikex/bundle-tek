## Selected connected design

These implementation decisions resolve the assessment; they are not implemented storage or new user permission to sign.

1. Use separate immutable v2 attempt, terminal outcome and private packet tables. Keep v1/ordinary preparation and packet tables unchanged. A prepared outcome is the v2 preparation record, independently bound to an admitted ordinary *summary format*, not an inserted ordinary row. This intentionally supersedes the older design's requirement to insert ordinary preparation plus a control-stream qualification event.
2. Bind each attempt to exact owner/request/journal/action, original terms and current control version/hash. Record an independent immutable attempt/result chain. Control history stays metadata-only; Pause/Stop/head changes invalidate in-flight publication without needing provider work to update the control head. New attempts never advance completed actions or spend budgets.
3. SQL chooses lease creation/expiry from its clock, capped at60seconds and the original approved finish. Derive the due pending action, exact wallet/revision, amount/lot and remaining original budget on the server. No HTTP wallet, amount, lot or budget fields. A session-buy Sell remains unavailable until real settlement can be replayed; no invented lot is allowed.
4. Count attempts from retained lease rows, regardless of whether provider work/refusal recording completes. Maximum3peraction and derived total persist across Pause/Resume/head changes. Gap is at least30seconds. No-outcome requests remain pending until the lease expires; prepared packets remain pending until their earlier packet expiry; a verified refused outcome ends pendency, but not the gap or attempt count. Late handlers cannot publish after lease/head/source expiry.
5. Claim the owner gate and lease atomically before provider work. If gate/source/head/ownership/reservation admission fails, retain neither. The provider must not reacquire that same gate. Existing v1 ordering and unrelated wallet-read gates stay unchanged. Cancellation is cooperative and does not prove a remote handler has stopped.
6. Same-ID POST and GET only recover the original retained attempt, never rerun quotes or renew times. A competing request receives the original pending ID. Validate its exact journal/head binding before recovering. A client timeout after lease creation keeps the original reminder; no automatic replacement write.
7. A successful outcome and its exact private packet are retained atomically with repeated source, wallet, lot, reservation, due/finish, lease and current-head checks. Expiry is the earliest order expiry, lease expiry and original finish. If head or source changed, refuse the whole result write; recovery still exposes the earlier lease. Aborted handlers do not initiate result writes. Unknown outcome writes are resolved by saved-only readback, not retried provider work.
8. Bound rows and derive total storage from the approved maximum attempt count. Initial targets are<=8KiBsummary and<=1,644base64packet characters, matching existing parsers; final schema/index/lease byte bounds must be measured and proven. No new total cap may silently drop approved actions. Recovery must use bounded pages, not giant SQL aggregates or whole packet vectors.
9. Add restrictive both-order ID isolation against ordinary/v1 preparations, signing intents and both receipt tables. V2 IDs cannot later be reused by another preparation. Application signing guards must recognize v2 identity as defence in depth; raw SQL intent INSERT refusal remains mandatory. No provider/program-ID-only permission is acceptable.
10. Add a separate saved-only attempt DTO and API with strict auth/same-origin/JSON/body/time limits and all authority flags false. Keep the existing journal DTO literals intact. The owned v2 UI gets a distinct unchecked fresh-preview request, durable request marker before POST, exact attempt/expiry/refusal display and GET-only recovery. No timers, automatic retry, signing or execution control.
