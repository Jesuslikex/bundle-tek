# Jito signed-packet recovery across panel changes, 28 October 2026

A synthetic test reproduced loss of a wallet-returned signature when the keyed inner bundle view remounted before the wallet prompt completed. The new bounded, non-evicting coordinator lives in the still-mounted outer panel and retains only an independently verified signature and its exact owner, project, session, bundle, manifest, packet and wallet context. It reconstructs and re-verifies the packet against the original manifest before showing it. It stores no seed or private key and uses no browser persistence.

The UI requires fresh, authenticated owner-scoped history before exposing recovery. An explicit owner-scoped exact-ID lookup finds a retained original even if it has fallen outside the 20-record history window. The server fences a supplied expected scope before actions, and the updated UI sends and verifies that scope. The scope is an identifier, not authentication or a confidentiality boundary. Account/context changes invalidate the view; an A-to-B-to-A transition requires a fresh owner-scoped read. Same-panel mutations and sign preparation are serialized before the first await; no new signature or submission happens automatically.

Signer hooks distinguish a provably unstarted prompt from an unknown post-invocation outcome. A short fresh owner-fenced read and exact packet revalidation precede signing. For local vault signing, derived secret buffers are cleared before the optional verified-retention callback; the original post-sign current/expiry check still applies. Retained packets require a new unchecked approval for manual registration or can be exported; expired or cancelled records remain export-only. Unknown or mismatched registration is not treated as confirmation. The existing sequential check remains informational, not a signing prerequisite.

**Limits:** this protects the reproduced inner-remount case while the outer panel remains mounted. A full panel unmount, page reload, tab closure or crash can still lose in-memory recovery or an unresolved wallet response. A fresh GET cannot make server/account changes atomic with an external wallet prompt or cover other tabs; existing server checks still apply. Same-origin code or debugging can inspect in-memory material, and an exported signed packet must be kept private. The unlocked vault session can remain in memory during the bounded five-second pre-sign check. This is not a confidentiality guarantee, durable recovery, provider qualification or funded proof.

Node 24 focused verification: 141 tests across 13 files passed in an independent final run; TypeScript and scoped typed lint/format passed. The `typescript/no-explicit-any` rule was suppressed for the scoped run because of existing occurrences in the shared warmup external signer, not represented as a clean unsuppressed check. The full script suite passed 88/88 on a hash-stable snapshot of the final code. The earlier full unit run at 1e22910 failed on Windows workerd cache access; it is not a full-suite pass for this source. No real wallet, signature, transaction broadcast, provider setting, hosted migration or deployment was used.
