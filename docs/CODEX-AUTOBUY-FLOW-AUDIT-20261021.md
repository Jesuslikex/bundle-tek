## Verified unit boundary

`counter-buy-preparation.ts` and its positive packet test use ExactOut: an original token target is fixed and SOL is capped. The existing manual Buy preparation passes a fixed native input amount, while `strategy-session-plan.ts` uses 9 decimals on Buy and token decimals on Sell. These sources support two candidate shapes, not one silently converted amount:

- Counter candidate: original decision/source identity, exact output-token target, freshly reviewed maximum SOL input and fee/rent ceiling.
- Timed or conditional candidate: exact SOL input, a fresh minimum token output, selected-wallet revision, source/trigger identity and fee/rent ceiling.

A future common session ledger must reserve each candidate's worst-case SOL debit and keep token target, input ceiling and fee units separate. Confirmed matching settlement may release a proven unused amount; signed/submitted/unknown state cannot. These are proposed implementation requirements, not authority granted by today's stored preview, nor observations of Proxima's internal model.

## Next implementation contract

1. Keep the existing manual Counter token-target ledger and draft/session formats intact. New Auto Buy session terms must name the amount units and supported quote asset explicitly. Initially support reviewed SOL input only; no stock-pair signing, inferred SOL units, unprotected slippage or generic support claim.
2. Build the durable session-level budget/lease primitive before runner admission, reusing the existing per-proposal reservation and single-approval infrastructure. Define one exact owned context and finite per-strategy/session and per-wallet spend/fee limits before execution. Distinguish intended input, confirmed spend, signed/submitted unknown holds and released pre-sign failures. A request timeout or local abort cannot prove that funds are available again. Stable order/event identities must prevent replay and repeated one-shot target fills.
3. Implement Counter, DCA and Limit admission with explicit source identity/freshness, direction and units. A feed observation is not a signed instruction review. Preserve honest cancellation and exact pending-operation state; retain limits through Pause/edit/resume and stop new admission while an original operation settles.
4. Compose the existing server preparation/review and browser-only signing controls for exact approved packets. Counter needs a real canonical review producer bound to its retained proposal/reservation; never promote a raw read-only native proof or assume every ExactIn parser supports ExactOut. Do not weaken review delays, wallet revision/custody/balance checks, min-output bounds, signing authorization, one-send or finalized/unknown recovery. Keep capability gates closed until their actual runtime qualification passes; do not replace execution with a fake Start that only saves a draft.
5. Expose a real owned UI with initial unchecked session consent, clear SOL/fee totals, strategy/overall limits, selected wallets/exclusions and transparent status/recovery. Wire through owned trading components; any protected Claude parent/layout slot needs an exact approved patch first. Rendered and provider evidence must qualify the completed flow before a parity claim.

This plan preserves the intended continuous Auto Buy end state. The audit is a dependency step and does not redefine completion around the already working planners or simulations. Source implementation can proceed without a funded test, deployment or changing providers. Any real-wallet unlock/sign/send or specific funded test still requires the user's separate authorization.

## Actual Opus 5.5 review and independent corrections

The focused read-only review confirmed the bounded missing continuous-Buy layer but corrected the initial map. It initially grouped supply sizing under Buy although `imported-trade-session.ts` explicitly restricts that to Sell DCA. It also omitted manual single-wallet Buy, capability-gated conditional Buy, the paired-operation Buy/settlement pattern and the existing Counter per-proposal/approval infrastructure. The corrected table above preserves those distinctions. Codex independently read the indicated prepare, conditional capability, Volume service, Counter reservation and 0077 trigger paths, rather than accepting the review as implementation proof.

The review also identified two known constraints that a Buy port cannot inherit: Auto Sell has a no-op run-lock fallback when Web Locks is unavailable, and its strategy/session accounting is local to the tab. Vault unlocking itself rejects missing Web Locks, so the lock observation alone does not prove a new unapproved trading path; no funded reproduction was attempted. Regardless, neither profile-local locking nor in-memory counters can establish a persistent multi-device SOL budget. No existing Sell runner or vault behavior was modified in this audit.

Preparation and signing share owner-level 15-second read gates. A future Auto Buy scheduler must coordinate with existing activity, preserve the gates and report delayed/overdue work honestly. Do not loosen throttles, burst missed cycles, silently shrink an ExactOut target to fit a budget, or reset financial counters on Pause/edit/reload. Signed/submitted/unknown holds survive interruption; release needs matching finalized debit/refund evidence or an explicit pre-sign expiry with no attached approval. These are proposed requirements, not newly enabled behavior.

The next implementation dependency is therefore the durable server-side aggregate budget and owned lease, with unit-explicit ExactIn/ExactOut candidate binding and reuse of the existing Counter source/approval guards. No new migration is reserved by this documentation-only audit; the next source task must recheck numbering/ownership before choosing one.
