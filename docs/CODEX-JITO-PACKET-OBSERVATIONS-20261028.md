# Jito packet observations during recovery

An explicit bundle recovery can now show a transient, sanitized report for each original packet using the existing signature-status RPC response. It distinguishes unregistered packets, provider-not-found results, unavailable or malformed statuses, and provider-reported processed, confirmed or finalized success/failure with a bounded slot. The report binds the exact bundle ID, manifest digest, state, ordered packet indexes and signatures; raw provider errors are not exposed. The UI labels the data as provider reports rather than verified receipts or proof of bundle atomicity.

The service retains its original record-only export for compatibility. The report is omitted if its record or signatures drift, the relevant bundle becomes terminal, or reporting cannot safely be constructed; a fixed unavailable message covers active signed recoveries without a report. The UI clears reports on account/context/history/action changes and revalidates the exact current signature vector. Existing database transitions, reservations, RPC call count, one-send behavior, signing and consent rules remain unchanged. Complete-success recovery errors still follow the existing error path and do not return the optional report.

Independent Node 24 verification passed 57 tests across five parser, service, route and UI files, plus four real-SQLite route-flow tests. Scoped typed lint and formatting passed. The implementing agent separately ran 83 additional Jito parent/remount/coordinator tests and full TypeScript. Independent source review found no blocker after unavailable-report guidance. All provider responses were synthetic; no real wallet, network submission, funded action, provider setting or deployment was used.
