# Owned Front/Back launch-layer planning

18 October 2026. This checkpoint connects the existing pure layer-terms model to authenticated owned storage and an API. It is the persistence boundary before the role editor. Full Front/Back funding, staged execution, recovery and Proxima parity are still incomplete.

## Source and role binding

`GET /api/launch/layers` reads either exact planning context (one JSON `context` parameter, capped at 2 KiB) or the latest/specific saved plan for an owned `projectId`. `POST` saves planning inputs only. The server supplies ownership, loads the current active saved workspace project, checks its exact saved timestamp and loads only that owner's Solana roster/folders. Caller-authored workspace, owner, envelope and authority overrides are rejected.

New targets are declared canonical public mint candidates. This does not prove possession, deployment or an account on-chain. Imported targets must be a current active Solana import owned by the same account, with matching imported revision, stored address and document address. Their source launch plan must be scheduled. The imported target's snapshot/revision is retained separately from the source launch project; a clone metadata reference is not used as proof of target ownership.

The developer for a new launch and every final holder must match the complete ordered selection already saved in the source project's launch-wallet settings. Front/Back/temporary wallets and the funder remain separate unique roster addresses. Active wallet and explicit folder references are rechecked. Public roster membership is not wallet-control proof, spendable balance, reserve admission or approval to sign.

Existing pure-model restrictions are unchanged: PumpFun/StonkFun Solana sequenced plans, exact holder count, StonkFun at most 12 Front wallets without Back/temporary layers, explicit buyer ceilings and exact delay units. Native network/rent/reserve budgets remain separate from token-quote atom ceilings. Stock units are saved catalog units only; no live mint/scaling or stock runtime admission is implied.

## Retention and concurrency

Additive migration `0109_launch_layer_plans.sql` follows the other Bundle chat's independent strategy migration 0108. A plan snapshot retains the complete source document, exact normalized model context, imported target snapshot when applicable, ordered role terms and both content fingerprints. Wallet snapshots retain only selected public wallets and referenced folders; their labels/names are blanked because they are not planning evidence. No balance, private key, vault payload, provider credential or ownership-proof signature is captured.

Plans are immutable and cannot be deleted. Exact snapshots are idempotent, including at the 100-plan per-project retention bound. Saving a different snapshot creates another record; it does not replace or activate an execution intent. Reopening the latest or a specific ID verifies the saved fingerprint and reconstructs the model under the captured context. A separately checked `current` boolean says whether the current source/target/selected references can still reproduce it. It is not an authorization. Historical plans stay readable after archive or revision changes; unrelated wallet changes do not invalidate selected roles.

The insert trigger atomically requires the active owner/project document/timestamp, matching new/imported target scope, exact saved developer/ordered holders and current active wallet/folder revisions. This closes the race between asynchronous hashing and insertion. SQL and the model require funding/signing/execution flags to be false, with null-safe SQL checks that refuse missing flags too. The fingerprint is unkeyed integrity evidence, not an authentication token or independent chain proof.

The authenticated API uses no-store, exact same-origin POST, exact JSON content type and a streamed 256 KiB body cap. Invalid UTF-8/JSON, foreign scopes and unsupported request fields refuse. The larger bounded body accommodates the existing bounded public-role model without a two-kilobyte limit that would silently exclude legitimate larger drafts. Storage errors are sanitized; missing planning storage is reported as unavailable rather than blaming a wallet change. Cancellation is checked before capture and persistence. No RPC, quote/order provider, transaction construction or financial action is called.

## Remaining integration

There is no layer editor or existing launch-handler consumer in this checkpoint. Saving this separate planning record does not change ordinary launch settings, select an active executable plan or cause existing deployer/holder signing paths to execute layers. The next role editor must explain this boundary and use the actual generated mint candidate where available; it must not offer an ordinary launch as though the layer record were being executed.

Still required: the role editor and explicit budget review, discovery of retained snapshots in the UI, independent required-funding/shortfall evidence, staged packet semantics and full code/custody/lifetime admission, separately unchecked funding/trade approvals, one-attempt execution and finalized failure/recovery accounting. Declared maximum budgets are not verified costs or cycling-capital requirements. Coordinated roles do not create additional independent holders or demand.

No new token/market/shell or wallet/vault UI, provider setting, credential, cron, stock/group gate, hosted SQL, push, deployment, wallet unlock, real signature or transaction was changed. The other Bundle chat owns strategy/session work; its files and migration 0108 are separate.
