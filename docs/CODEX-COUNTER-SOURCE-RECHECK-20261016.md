# Counter contributing-source rechecks

The owned Counter Buy settlement preview now refuses missing, stale or changed contributing-source evidence. A target can aggregate several buffered signals, so admission covers every nonzero contribution since the preceding proposal, not just the last trigger. The preceding proposal is excluded from the next target. No Counter execution, approval or signing is enabled.

## Retention and compatibility

New evaluator decisions retain detached copies of the original pool/trade context and confirmed movement. The existing identity and fingerprint encoding are unchanged. Ledger validation binds retained source context, token precision, transaction identity and fingerprint to the saved decision. Existing plans without this optional source field remain readable; no migration or history backfill occurs. Immutable prior-decision database rules remain unchanged, and an old proposal missing any contributing source refuses before provider I/O. Users need newly evaluated, retained sources; the old ledger is not silently promoted to current evidence. The existing one-megabyte document guard still bounds retained plan growth.

## Read-only preview composition

After owned plan/project/wallet/exclusion admission, the service reobserves each contributing transaction with the existing configured movement observer, then rechecks the owned snapshot before preparation. After original-packet simulation and gross settlement, it repeats source observations and the owned snapshot check before returning a summary. Reads are sequential, abortable and covered by the existing 45-second request deadline; there is no retry or alternate-provider loop.

Each observation must match the retained context, exact fingerprint and block time. The evaluator reconstructs that contributor against its historical prefix and compares exact outcome, probability draw, contribution and target. It uses the retained draw, never a new probability roll. Excluded source wallets are still excluded. A changed buffered contributor refuses the entire target. The evaluation route's activation and five-minute trade/observation freshness bounds are also applied to the complete contributing set at preview time. This explicitly means a buffered aggregate containing a trade older than five minutes is not eligible for this current-source preview, even if it was valid when first evaluated. No amount, trigger, minimum, probability or exclusion rule is loosened.

The public response reports `sourceRevalidated: true`, contributing trade count, final recheck time and source-valid-until time only after those checks pass. Preview expiry is capped by source expiry and the prepared packet's expiry. A packet that expires during the final source reads is refused. The client requires the checked count to match the selected proposal's contributing block and validates the source timestamps as well as existing context/amount/authority checks. The Counter component describes the check and shows its count/time. Source-admission refusals map to 409; unknown provider errors remain sanitized 502 responses. No packet bytes are returned.

This rechecks the existing confirmed transaction/movement classification. It does not prove finalized settlement, independent membership of that transaction in the reported pool, program-code admission, or durable execution authorization. The response still has programCodeAttested, reservationCreated, approvalAllowed, signingAllowed and executionAllowed false. Immutable packet/budget storage, reservations, explicit consent, signing, submission and recovery remain open.
