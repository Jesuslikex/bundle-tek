## Original preparation, not another approval

The server can save an awaiting-signature approval and reserve a wallet before its response becomes unreadable. The executor now retains a detached, frozen reference to the exact original project/revisions, preparation, wallet, mint, amount and packet hash. An unreadable review or a local signer refusal without a returned packet stops automatic work instead of trying another wallet or repeatedly creating reviews. The runner keeps the reference even if Stop was pressed first. Unsent amounts are not counted as sold; queued amounts are restored only while the strategy was still running, then the run stops. No server reservation is automatically released.

The modal pins the latest100 original review references across explicit runs within that mounted context; capacity eviction is disclosed. New snapshots cannot replace the first reference with a newer unrelated preparation. A known review409 is marked as a conflict; if no matching record exists, the UI explains that another approval/reservation/context may be involved instead of suggesting that the new preparation is indefinitely pending. The list is local metadata, not durable session storage; reload or a project/wallet context replacement clears it. Saved approval history remains the reload path. No packet, signature or key is manufactured for an unreadable review.

## Manual unsigned cancellation

An awaiting-signature record with no recorded signature exposes a separate initially unchecked approval. The button sends only the existing action:cancel and exact intent ID. The unchanged server independently requires the owned awaiting-signature state, null signature and no Jito bundle binding in its atomic cancellation statement. Signed/submitted/finalized/signature-bearing or bundle-bound records cannot be cancelled through this control. A definite409 is called a refusal; an unreadable/lost response remains unknown.

Both a valid cancellation acknowledgement and an unknown write outcome require an explicit saved-status GET for that same intent before another cancellation consent can be given. There is no automatic retry, compensating write, allowance refund, counter reconciliation or strategy resume. Successful matching reads clear consent. Cancellation is disabled with a reason during an active/busy/settling run or another unresolved cancellation; disabling it withdraws previously checked consent without remounting an in-flight child.

Parent history reads, filtering and preparation re-reads are synchronously blocked while their child cancellation is in flight or needs its status read. The child recovery GET remains usable, including after sign-in/access is restored. An ordinary permitted history refresh remounts cancellation controls with fresh unchecked consent. This prevents the parent-refresh reset found during review. A synchronous modal-wide namespaced guard also blocks new Run actions before vault unlock while cancellation is in flight or needs status recovery. Only matching explicit reads clear those guards. Since new runs are the only producer of new reminder entries, pending cancellation panels cannot be evicted by the100-entry bound while this guard is held. The actual-modal test verifies Run remains disabled before the cancel reply and after its acknowledgement until the saved-status read succeeds. This is per-view coordination, not a durable/global cancellation-intent service. After full navigation/reload a new explicit owned GET is still required; repeated manual requests are ultimately protected by the existing server CAS, not a new financial ledger.

Focus is tracked only for each explicit request. Outside pointer/focus/window-blur interactions suppress restoration, and listeners are removed on completion, cancellation and unmount.
