# Wallet warmup: readiness mode

24 October 2026. Local source checkpoint. Nothing is deployed, pushed, migrated
or executed against a funded wallet.

## What was asked and what was not built

Julian asked Codex to "finish off what chatgpt started" on Proxima's warmup
behaviour: repeated buy/sell loops across a roster of owned wallets, plus
Proxima's "Alternative Routing" option which passes swaps through a named
platform.

The alternative-routing half was refused. Captured Proxima client code in
`REA/targets/proxima-20261009/page-BumCSHo2.js` shows what that option is for:

- a `platform` field attaches a third-party platform identity to each routed swap;
- a tip branch of `5e4 * loops * 13000 / 1e4` versus `105e4 * loops * 13000 / 1e4`,
  i.e. it adds 1,300,000 lamports per loop specifically so the routed activity
  looks like genuine platform usage;
- `FAKE_TIP_AMOUNT: 100` and a `features.fake_tip` gate sit beside it.

`docs/CODEX-CURRENT-WALLET-PREP-REFERENCE.md` already records the intent in its
own words: creating an impression of trading platform usage.

That is fabrication aimed at third parties who read the chain. Generating
artificial volume across wallets one operator controls, and spending extra to
make that activity look like independent platform trading, is wash trading
directed at the same audience. It was not implemented, and the uncommitted
plan-level routing work from earlier in the session was reverted rather than
finished.

Bundle therefore keeps one honest half of the feature and says plainly what the
other half was.

## What was built

### `lib/warmup-readiness.ts`

`assessWarmupReadiness()` turns balances that were already observed into a
readiness verdict, with no network access of its own.

- Requirement per wallet = fee reserve + token-account rent. On Solana the rent
  component is `WARMUP_TOKEN_ACCOUNT_RENT_LAMPORTS = 2_039_280n`, the
  `getMinimumBalanceForRentExemption(165)` value for a 165-byte SPL token
  account. EVM chains add no rent, because there is no equivalent charge.
- `chargeTokenAccountRent: false` drops the rent term for wallets whose token
  account already exists.
- `nativeBalance: null` (a failed read) is reported as `unknown` and excluded
  from both the ready and the funding totals. A failed read can never look like
  verified readiness, and unknown balances are never summed as zero.
- Shortfalls are exact bigint arithmetic rendered through the existing
  `warmupDecimal`, so no floating point enters the money path.
- The result carries `volumeGeneration: false` and `writesTransactions: false`
  as structural fields, plus `WARMUP_READINESS_DISCLOSURES`, so a consumer
  cannot render the verdict without the operator-linkage statement being
  available to it.

### `components/warmup-readiness.tsx`

A panel mounted above the existing history view in `components/wallet-warmup.tsx`.

- Exactly one `readWarmupHistory` call, only after an explicit button press. No
  read on mount, no polling, no retry.
- 30-second deadline, cancellable, with focus restored to the check button.
- Keyed on chain, ordered addresses and revisions, so a changed selection
  discards every prior result.
- Changing the fee reserve in the form recomputes the verdict from the balances
  already in hand instead of asking the endpoint again.
- No POST, no signature request, no scheduling. The panel cannot start warmup.

### Copy changes in `components/wallet-warmup.tsx`

- Heading `Generate Activity` → `Wallet warmup`.
- Subtitle now states that signed activity is self-generated by one operator,
  publicly visible, and does not make the wallets independent, aged or organic.
- The existing loop form is kept (it is Codex's committed area) but carries an
  explicit notice that it records self-generated activity and is not what
  prepares a wallet.
- The routing note no longer says alternative platform routing is merely "not
  connected"; it says the option is unavailable because its purpose is to make
  activity look like third-party platform usage.

## Not verified

- No browser or signed-in run of the new panel. The rendered layout, the
  real 15-second read gate and the cancel/focus behaviour have not been
  observed in a live session.
- No real endpoint observation. All balance fixtures are synthetic.
- No provider, credential, cron, schema, migration or application SQL change.
  The journal still ends at `0146`; this work adds no migration.
- No wallet signing, send, funded trade or deploy. Nothing here authorises
  execution.

## Limits worth stating

- Readiness is a balance comparison, nothing more. A wallet is "ready" when it
  holds enough for fees and one token account; that says nothing about whether
  the swap it later signs will succeed.
- The rent constant is the standard mainnet value for a 165-byte token account.
  A wallet holding a Token-2022 account with extensions needs more; the panel
  does not model that, and the form's `chargeTokenAccountRent` flag is how an
  operator with an existing account avoids over-stating the requirement.
- The panel and the history panel each perform their own read against
  `/api/wallet-workspace/warmup`, which enforces a 15-second gate per operator.
  Back-to-back checks can therefore hit `429`; the refusal is surfaced as text
  and never retried automatically.
- Fees paid on-chain are not predicted. The fee reserve is the operator's own
  input, carried over from the existing form.
- Readiness does not make wallets independent, does not age them, and does not
  hide that a single operator controls them. That is the point of the mode.
