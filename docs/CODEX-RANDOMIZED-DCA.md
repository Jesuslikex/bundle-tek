# Reviewed randomized DCA allocation

This continuation implements minimum/maximum per-cycle amount controls following fresh REA evidence in CODEX-PROXIMA-RANDOM-DCA-LIVE.md. Proxima's actual form exposes those controls in percentage-of-supply units. This implementation uses explicit SOL inputs for Buy and token inputs for Sell, with the existing finite cycle schedule and total budget. It does not claim backend/distribution equivalence or close the remaining percentage-unit and strategy/session ending requirements.

The composer has Even split and Randomized within bounds modes. Randomization runs only when the user clicks Generate random allocation. Its preview fixes every cycle amount before saving. Changing the budget, cycle count, wallet/revision, project context or bounds invalidates the preview; ordinary renders, failed-save retries, preparation, signing and receipt recovery never generate replacement amounts. Saved history includes the reviewed bounds. Every cycle retains separate explicit signing and submission approval.

The generator uses Web Crypto 64-bit draws and rejection sampling, without floating-point amounts or modulo bias. For each cycle it draws uniformly from the currently feasible interval, leaving enough budget for the remaining cycles within their minimum/maximum. The final cycle is determined by the remainder. This is sequential conditional sampling, not a uniform draw from every possible whole-plan allocation. Degenerate equal-bound/forced allocations need no random draw. Unavailable/invalid entropy fails rather than falling back to Math.random.

Random metadata is canonical bounded-dca-allocation-v1, with minimumRaw, maximumRaw and separately declared totalRaw. The server validates this metadata independently of the client generator, enforces positive u64 amounts, one current wallet/revision, exact declared budget conservation and every cycle's bounds. A modified allocation whose amounts remain within bounds but exceed the declared total is rejected. Existing sessions without this metadata keep their unchanged even-split contract. Persisted terms and exact cycle captures are reused through the genuine signing/session routes; amount metadata adds no new migration or worker activation.
