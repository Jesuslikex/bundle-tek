The comparison below describes the source before the unified reader. The new local implementation is documented in `CODEX-TOKEN-OPERATION-HISTORY.md`: five server-scoped sources now share pagination and category filtering in the open workspace. Broader operation sources, skipped-wallet job outcomes and rendered/hosted validation remain incomplete. The current `components/imported-token-projects.tsx` renders project revisions, preparation history, trade history and approval history as separate sections following the token workspace. `components/imported-token-history.tsx` correctly limits its records to project revisions; these must not be relabelled as trade receipts. `components/workspace-activity.tsx` already aggregates several operation sources at account scope, including immutable Jito transitions, but it is not an owned-token operation-history endpoint or a complete token history.

Current contracts inspected during the frozen run: `/api/imported-projects/signing-activity` already accepts projectId and verifies ownership and project-bound cursor anchors. It retains reviewed/signed/submission/finalized/failed/cancelled states, raw amounts and optional failure evidence. `/api/imported-projects/jito-activity` scopes by owned bundle rather than project, so an account feed must not simply be filtered client-side and called a complete token feed. Project activity and preparation-activity currently have separate account-scope cursor conventions. Session events retain immutable session context and approval-entry detail. A unified reader must bind every source to the owned project server-side and preserve existing source validation.

The unified endpoint should paginate a single total order over retained source identity, timestamp and source-specific tie-break keys, rather than merging unrelated first pages and declaring older coverage complete. Apply selected category filters before pagination, bind cursor anchors to owner/project/filter context, and label unavailable optional source tables explicitly. Existing signing/session records can represent the same approval transition, so the projection must define whether they are one operation with nested transitions or separate explicitly labelled event rows. Never double-count those rows as financial executions. Baseline captures remain labelled retained states, with no fabricated prior transitions. Regression coverage must include equal-time boundaries, multiple projects/owners, source identity collisions, category changes, failed/cancelled entries, missing optional storage and duplicate approval representations.

A real token-history integration should unify owner/project-bound operation records with stable pagination and explicit source coverage, then offer action filters and expandable details inside the open chart workspace. It must preserve failed, skipped, pending and finalized distinctions rather than presenting preparations or approvals as executed trades. Wallet movement observations remain a separate history source. Existing reviewed-signing actions must retain their current consent and freshness checks. Avoid simply hiding independent historical panels behind tabs and claiming this implements a unified operation timeline.
