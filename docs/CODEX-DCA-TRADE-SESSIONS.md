# Finite DCA sessions, 13 October 2026

Bundle's token workspace can now save scheduled Buy or Sell DCA sessions for one current Solana wallet. The composer previews 2 to 25 cycles, an exact total input budget, UTC eligibility times and an interval of 1 to 86400 seconds. Integer arithmetic distributes remainder atoms to the earliest cycles and rejects budgets too small to fund every cycle. Buy inputs use SOL precision; Sell inputs use the imported token's precision. Network fees and fresh available funds remain separate per-cycle checks.

Saved DCA terms use `imported-trade-session-v3` with `strategy: DCA`. Only this format admits repeated wallets, and all cycles must use the same current wallet revision and canonical even split. Earlier v1/v2 session contracts retain distinct wallets. The API reuses immutable idempotent session IDs, owner/project/wallet guards, retained control/history and the existing per-entry preparation, approval, registration, submission and finalized receipt workflow. Every due cycle needs explicit approval; a plan is not shared signing consent. Saving locks the surrounding session controls until completion, and an ambiguous failure retries the same immutable request. A mismatched saved response cannot enter the session list.

Append-only migration `0074_dca_trade_session_timing.sql` extends all three existing database due-time guards to recognize valid v3 DCA schedules. Earlier 74 SQL files and journal entries are unchanged. No schema model changed; this custom migration updates triggers. DCA creation returns 503 without saving if any v3 timing guard is absent. Capture packets retain the existing v2 exact entry identity and due time, bound to the full saved terms hash. The DCA UI does not offer the atomic Jito grouping panel, because these cycles are intentionally spaced.
