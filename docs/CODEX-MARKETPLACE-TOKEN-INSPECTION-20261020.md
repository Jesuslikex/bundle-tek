# Owned token-account inspection foundation

20 October2026. Source-only continuation of0f60969. This is a server collector, exact informational contract and client-admission foundation. It is not mounted to an API or seller screen in this checkpoint.

The existing seller check covers the native SOL account. This next collector enumerates provider-returned token accounts owned by one exact saved seller wallet, separately under the original Token Program and Token-2022. It uses the configured ordinary mainnet endpoint and existing bounded precision-preserving RPC transport/pacing. No provider setting, credential or other wallet reader changes.

## Read and decoding contract

The caller must authenticate/authorize the operator and supply the actual owned inventory reader. Before provider reads, the collector admits the inventory and exact wallet revision. It binds the complete selected retained wallet evidence using canonical SHA256, excluding only the derived advancing age counter. After provider reads, the inventory is read/admitted again and this binding must still match. Removed/archived/changed sources refuse; it is not a general seller authorization service.

Five sequential RPC calls verify genesis, capture a confirmed baseline, enumerate each token program with the prior observed slot as its next minimum floor, then obtain a final slot. Per-program slots remain separate. Reversed floors and spans above the existing32-slot consistency limit refuse;32 is accepted. No Clock or stock-runtime/signing check changes. The operation expires at60seconds, cancellation is checked across reads/decoding/final hashing, and there are no retries. Each enumeration response is bounded to2MiB, metadata reads to16KiB; at most200 accounts across both programs are supported. Oversized/partial/failed responses refuse the whole result instead of truncating or returning an empty list.

Each account is decoded from canonical base64 bytes with exact program/executable/space/address/owner bindings. The original Token Program requires165bytes. Base-state decoding records exact u64 raw token units, account lamports, initialized/frozen state, delegate and delegated allowance, close authority and optional native reserve. All COption tags are validated; an absent delegate cannot carry a nonzero allowance, and native reserve cannot exceed account lamports. Inactive option payload bytes do not invent an authority.

Token-2022 requires the account discriminator before TLV entries. Known account extension records are decoded/re-encoded with the installed official token-2022 SDK. Mint-only, duplicate, unknown, truncated or noncanonical extensions refuse. Reserved zero padding is accepted. Recognized account extension names are reported; their transfer, confidential or mint-level semantics are deliberately not assessed. Account byte hashes bind the canonical base64 text, labelled `encodedDataSha256`, not a signature or proof of provider truth.

Results retain all accounts, sorted by canonical account address, and count accounts with nonzero raw amounts, frozen state, delegates, foreign close authorities and decoded extensions. Different mints' raw units are never combined or displayed as a price, P&L, sale credit or transferable amount. Missing coverage never means zero assets. No current control, full asset/authority, extension semantics, sale qualification, payment, delivery or signing flag is enabled.

The strict client contract/admission verifies exact selection and source-wallet hash, canonical times/expiry, both required program entries/order/floors, every account's program-slot/wallet binding, count conservation, canonical ordering/uniqueness, exact units, authority consistency, extension lists and all false capability flags. Full raw bytes are not sent to this client contract, so client admission does not independently decode provider bytes; it admits the server's informational snapshot only.

## Scope and reference

Coverage is explicitly limited to provider-returned owned accounts under these two programs. It does not prove provider completeness, inspect token mint authorities/permanent delegates, decrypt confidential amounts, cover stake/compressed assets/other programs, or establish an empty/sale-ready wallet. Token-account authority fields and mint-level authority distinctions follow the [official Solana token documentation](https://solana.com/docs/tokens), [token basics](https://solana.com/docs/tokens/basics) and [permanent delegate documentation](https://solana.com/docs/tokens/extensions/permanent-delegate). The wire layout and TLV codecs were checked against the installed official SDK source; no package was changed.
