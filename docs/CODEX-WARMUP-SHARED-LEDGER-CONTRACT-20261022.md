## Confirmed current storage

All journal migrations through `0136_auto_buy_budget_ledger` were loaded unchanged into disposable native SQLite with foreign keys enabled. No live or application database was opened. The new test exercises actual resulting constraints and triggers, without dropping guards or installing parent-table projections. Synthetic direct SQL rows deliberately do not establish HTTP admission, signature validity, receipt verification or on-chain execution.

`solana_swap_reservations` bridges warmup/imported intent holds into `solana_execution_reservations`. The final latter table still permits only warmup/imported/withdrawal scopes, with one row per owned wallet. A new execution scope cannot simply be inserted. A competing withdrawal fails atomically after either swap scope is reserved; either swap scope also fails after a withdrawal, with no partial parent/event/bridge rows. Different owners and wallets remain independent. State changes propagate through the bridge. The extended tests also exercise SQL-valid ordinary warmup/imported parent preparations and intents: insertion, signed/submitted transitions, failed-state release, refused reactivation while a withdrawal holds the wallet, successful reactivation after explicit unsigned withdrawal cancellation, parent deletion and retained signature registration. These are minimal storage-valid parents, not valid server-reviewed packets.

`solana_swap_signatures` bridges into `solana_execution_signatures`. A previously registered swap signature rejects withdrawal registration and vice versa, with rollback. Both are owner-scoped; this is not a chain-wide signature registry for every launch/Jito/automation family. The shared indexes already prevent naive warmup/imported signature reuse. Do not report an arbitrary duplicate-receipt vulnerability from a string search.

These registries are not an immutable outcome journal. Direct deletion of a swap registry row deletes the execution bridge. Native withdrawal's SQL failed transition also releases the bridge without requiring a non-null failure receipt. This is not a demonstrated HTTP bypass: `app/api/wallet-workspace/withdrawals/route.ts` obtains finalized transaction data, refuses null, and decodes its exact native/token receipt before writing the outcome; its funding-recipient-scoped duplicate guard also accounts for failed rows lacking evidence. Ordinary warmup/imported parent state changes out of active states and parent deletion likewise release the swap/execution bridge at the storage layer; the full-schema parent tests demonstrate this for ordinary unbound synthetic parents. This does not establish that a financial API permits arbitrary state mutation. The withdrawal reject_signing branch also accepts a user assertion that no signature was produced before cancellation; that existing UX is not adopted as an independent unknown-outcome proof for new execution. Future warmup must not use a bare failed state or missing signature status as evidence of non-landing.

## Receipt and lot visibility

`saveWarmupSellReceipt` uses the verified original packet/receipt, an exact saved Buy link and integer consumed units. Its application batch inserts a Sell only while the original Buy document and remaining raw units still match, decrements that Buy once, and finalizes the signing intent only when its receipt exists. `wallet-warmup-progress-server.ts`, `warmup-receipt-history.ts`, `wallet-warmup-session-provider-core.ts`, runtime receipt-floor and token-operation history read these tables. A second execution-only Buy/Sell table would be invisible to these consumers unless they are deliberately integrated. The current decrement is application-batch logic, not a database-wide consumption trigger. Its success result checks the receipt insert and remaining-unit update, not the final intent update; the receipt INSERT itself does not require that exact finalized intent/registered signature. Existing callers may enforce those facts, but the sink alone does not prove them. Both storage designs need atomic source/intent/signature/consumption admission for new execution, and must reject a successful-looking receipt that cannot join the exact finalized lineage.

Imported acquisition allocation and retained sale evidence are separate owned project ledgers. Imported sale evidence replays its original imported receipt/preparation/registered signature; it is not arbitrary external sale evidence. A token balance decrease cannot tell which fungible acquisition lot was consumed. Existing warmup receipts explicitly disclose that external transfers and pending transactions are not reconstructed. Do not silently turn those bounded saved-history projections into whole-chain allocation claims.

Before choosing storage, evaluate whether the new version can use the existing verified shared Buy/Sell receipt tables with distinct v3 preparation/action bindings. `0134` forbids old v2 attempts from entering signing/receipt sinks; do not edit or bypass that rule. Distinct new IDs are not blocked by the specific 0134 receipt-isolation predicates: they reject matching v2 attempt receipt/preparation IDs. That alone permits nothing financially. Ordinary sink reuse also needs exact manual preparation and finalized signing-intent lineage for settlement-source joins, plan/revision/cycle binding, compatible per-plan history capacity, and warmup_signing_events for operation-history visibility. Inserting another receipt on a plan invalidates that plan's old v2 contexts because their captured Buy/Sell counts must remain exact. This is an intentional closed outcome, not migration permission or a silent consent upgrade. Prove manual signing paths cannot admit a new execution-bound preparation without its distinct consent and authorization. Reusing the lineage and sink is a question to prove, not implemented permission. If new receipts are stored separately, all manual, progress, runtime-floor, receipt history and operation-history consumers need one exact shared projection and atomic consumption admission. In either design, the new root retains its immutable initial source independently of later verified settlements; it never rebases a cursor to latest receipt counts.
